# ТЗ: маршрутизация опросников по клиникам и полям Bitrix24

Дата: 2026-05-04

## 1. Цель

Добавить в административную часть Opros раздел маршрутизации опросников.

Раздел должен позволять администратору выбрать клинику, назначить для нее опросник по умолчанию и настроить правила выбора опросника на основании полей сделки Bitrix24.

Ключевое архитектурное требование: новая маршрутизация не должна встраиваться в медицинскую JSON-логику опросников и не должна требовать переработки `SurveyEngine`. Выбор опросника выполняется отдельным backend-слоем до старта прохождения опроса.

## 2. Текущая архитектурная база

В проекте уже есть:

- `SurveyConfig` - таблица опросников с JSON-конфигурацией: `backend/app/models/models.py`;
- `SurveySession.survey_config_id` - привязка сессии к конкретному опроснику;
- Bitrix webhook, который генерирует короткую ссылку и записывает ее в сделку: `backend/app/api/v1/endpoints/bitrix_webhook.py`;
- Bitrix-клиент с методами получения сделки, обновления полей и получения metadata поля: `backend/app/services/bitrix24.py`;
- admin-сессия SQLAdmin и frontend-страницы редакторов, защищенные через `/admin/api/session`;
- отдельный production worker `session-cleanup`, который можно использовать как пример для нового worker-процесса синхронизации.

Новая функция должна использовать эти точки расширения, а не заменять существующий flow опросника.

## 3. Термины

- Клиника - бизнес-направление/филиал, отображаемый администратору как человекочитаемое название.
- Воронка Bitrix24 - `CATEGORY_ID` сделки Bitrix24.
- Опросник - запись `SurveyConfig`.
- Правило маршрутизации - набор условий по CRM-полям, который выбирает конкретный опросник.
- Опросник по умолчанию - fallback-опросник клиники, используемый если ни одно правило не подошло или произошла ошибка.
- CRM-поле - поле сделки Bitrix24, полученное из `crm.deal.fields`.
- Списочное поле - CRM-поле с фиксированными вариантами значений, например enumeration.

## 4. Бизнес-правила

### 4.1. Клиники

Клиника может соответствовать одной или нескольким воронкам Bitrix24.

Связь клиника-воронки не настраивается визуально. Она задается в коде или конфигурации backend.

В интерфейсе администратор видит только название клиники.

Рекомендуемый формат backend-конфигурации:

```python
SURVEY_ROUTING_CLINICS = (
    {
        "key": "novosibirsk",
        "title": "Новосибирск",
        "bitrix_category_ids": ("0",),
    },
    {
        "key": "kemerovo",
        "title": "Кемерово",
        "bitrix_category_ids": ("1",),
    },
    {
        "key": "yaroslavl",
        "title": "Ярославль",
        "bitrix_category_ids": ("3",),
    },
)
```

Если текущие клиники должны отличаться от doctor portal bucket-логики, для новой функции создается отдельная конфигурация. Не нужно напрямую переиспользовать `doctor_portal_routing.py` как единственный источник истины, потому что doctor portal и выбор опросника имеют разные бизнес-задачи.

### 4.2. Настройки клиники

У каждой клиники есть:

- собственный опросник по умолчанию;
- собственный независимый список правил;
- собственные приоритеты правил.

Приоритеты правил сравниваются только внутри выбранной клиники.

### 4.3. Правило

Правило содержит:

- название;
- активность;
- выбранный опросник;
- одно или несколько условий;
- логику условий `AND` или `OR`;
- приоритет.

Правила применяются только если они активны.

Правила проверяются по приоритету. Если подходит несколько правил, выбирается правило с самым высоким приоритетом.

Рекомендуемая трактовка приоритета: большее число означает более высокий приоритет. UI должен показывать правила в порядке фактической проверки. Если будет выбран формат "сверху вниз", backend все равно должен хранить явное числовое значение приоритета.

### 4.4. Условие

Условие содержит:

- поле CRM;
- оператор;
- значение.

Операторы первой версии:

- равно;
- не равно;
- содержит;
- не содержит;
- заполнено;
- не заполнено.

Для операторов `заполнено` и `не заполнено` значение не требуется.

### 4.5. Fallback

Если ни одно правило не подошло, используется опросник по умолчанию выбранной клиники.

Если произошла ошибка при получении сделки, чтении правил, сравнении условий или выборе опросника, используется опросник по умолчанию выбранной клиники.

Если клинику определить невозможно, используется отдельный глобальный fallback. Его нужно явно задать в настройках backend или запретить обработку такой сделки с понятной ошибкой. Рекомендуемый вариант для production: глобальный fallback-опросник, чтобы Bitrix-сценарий не ломался из-за нестандартной воронки.

## 5. Момент выбора опросника

Выбор опросника выполняется в момент генерации ссылки в Bitrix webhook, до записи ссылки в сделку Bitrix24.

Текущий flow:

1. Bitrix24 вызывает `/api/v1/bitrix/webhook`.
2. Backend генерирует JWT.
3. Backend сохраняет JWT по короткому коду в Redis.
4. Backend формирует `/s/{short_code}`.
5. Backend записывает ссылку в поле сделки Bitrix24.
6. Пациент открывает ссылку.
7. `/survey/start` сейчас выбирает первый активный `SurveyConfig`.

Новый flow:

1. Bitrix24 вызывает `/api/v1/bitrix/webhook`.
2. Backend получает сделку Bitrix24 через `crm.deal.get`.
3. Backend определяет клинику по `CATEGORY_ID`.
4. Backend применяет правила выбранной клиники.
5. Backend получает итоговый `survey_config_id`.
6. Backend создает JWT или Redis-маппинг короткой ссылки с `survey_config_id`.
7. Backend формирует `/s/{short_code}`.
8. Backend записывает ссылку в поле сделки Bitrix24.
9. Пациент открывает ссылку.
10. `/survey/start` использует `survey_config_id`, выбранный на этапе webhook.

Публичный формат ссылки `/s/{short_code}` менять не требуется.

## 6. Хранение выбранного опросника в ссылке

Нужно расширить данные, связанные с короткой ссылкой.

Допустимые варианты:

1. Добавить `survey_config_id` в JWT payload.
2. Сохранять в Redis не только JWT-строку, а JSON-структуру с JWT и `survey_config_id`.

Рекомендуемый вариант: добавить `survey_config_id` в JWT payload, потому что текущий код уже передает JWT из Redis в frontend как `resolved_token`, а `/survey/start` проверяет JWT через `verify_token`.

Требования:

- `survey_config_id` должен быть необязательным для обратной совместимости со старыми ссылками;
- если `survey_config_id` отсутствует, `/survey/start` использует прежнее поведение или глобальный fallback;
- если `survey_config_id` указан, `/survey/start` загружает именно этот `SurveyConfig`;
- если указанный опросник удален или неактивен, используется fallback клиники или возвращается управляемая ошибка. Рекомендуемый вариант: fallback клиники, если клинику можно определить по сделке.

## 7. Модель данных

### 7.1. Таблица настроек клиник

`survey_routing_clinic_settings`

Поля:

- `id`;
- `clinic_key` - строковый ключ клиники из backend-конфигурации, unique;
- `default_survey_config_id` - FK на `survey_configs.id`;
- `is_enabled` - включает маршрутизацию для клиники;
- `created_at`;
- `updated_at`.

В UI отображаются только клиники из backend-конфигурации. Если для клиники нет записи в таблице, backend возвращает ее с пустыми настройками.

### 7.2. Таблица правил

`survey_routing_rules`

Поля:

- `id`;
- `clinic_key`;
- `name`;
- `is_active`;
- `survey_config_id` - FK на `survey_configs.id`;
- `condition_logic` - `AND` или `OR`;
- `priority`;
- `created_at`;
- `updated_at`.

Индексы:

- `clinic_key`;
- `clinic_key, is_active, priority`.

### 7.3. Таблица условий

`survey_routing_conditions`

Поля:

- `id`;
- `rule_id` - FK на `survey_routing_rules.id`;
- `crm_field_id` - например `UF_CRM_...` или стандартное поле `CATEGORY_ID`;
- `operator`;
- `value` - строковое значение или JSONB для будущих расширений;
- `created_at`;
- `updated_at`.

Для первой версии достаточно хранить `value` как `String/Text`, но JSONB гибче для будущих multi-value условий.

### 7.4. Кэш CRM-полей Bitrix24

`bitrix_crm_fields`

Поля:

- `id`;
- `entity_type` - первая версия: `DEAL`;
- `field_id` - системный ID поля Bitrix24;
- `title` - человекочитаемое название поля;
- `type` - тип поля Bitrix24;
- `is_list` - признак поля со списком вариантов;
- `is_active`;
- `raw_metadata` - JSONB с исходными metadata Bitrix24;
- `synced_at`;
- `created_at`;
- `updated_at`.

`bitrix_crm_field_options`

Поля:

- `id`;
- `field_id` - FK или строковая связка с `bitrix_crm_fields.field_id`;
- `option_id` - стабильный ID значения Bitrix24;
- `label` - отображаемый текст;
- `sort`;
- `is_active`;
- `raw_metadata` - JSONB;
- `synced_at`;
- `created_at`;
- `updated_at`.

Для списочных полей в правилах хранится `option_id`, а в интерфейсе показывается `label`.

## 8. Синхронизация CRM-полей Bitrix24

Backend должен регулярно получать список полей сделки из Bitrix24 и сохранять его в базе.

Источник:

- `crm.deal.fields`.

Периодичность:

- ежедневно в 00:00 по timezone `Europe/Moscow`.

Инфраструктурное требование:

- не запускать расписание внутри FastAPI lifespan, потому что production backend работает в нескольких gunicorn workers;
- реализовать отдельный worker-процесс или расширить существующий worker-паттерн из `session-cleanup`;
- worker должен быть идемпотентным.

Рекомендуемый новый сервис в `docker-compose.prod.yml`:

- `bitrix-field-sync`;
- команда: `python -m scripts.sync_bitrix_crm_fields`;
- внутри скрипта цикл с расчетом времени до следующего запуска в 00:00 Europe/Moscow;
- ручной запуск должен быть возможен той же командой с флагом `--once`.

Поведение синхронизации:

- новые поля добавляются;
- существующие поля обновляются;
- исчезнувшие поля не удаляются физически, а помечаются `is_active=false`;
- варианты списков обновляются аналогично;
- ошибки Bitrix24 логируются, но не очищают старый кэш.

## 9. Сравнение условий

Backend resolver должен работать с данными сделки Bitrix24.

Нормализация:

- `None`, пустая строка, пустой список считаются незаполненным значением;
- строки сравниваются после `strip`;
- для `равно` и `не равно` первая версия может использовать точное строковое сравнение;
- для `содержит` и `не содержит` используется case-insensitive substring;
- для списочных полей сравнивается сохраненный `option_id`, но reason/debug может показывать `label`;
- если поле multi-value, условие считается подходящим, если хотя бы одно значение удовлетворяет оператору.

Операторы:

- `equals`: значение поля равно значению условия;
- `not_equals`: значение поля не равно значению условия;
- `contains`: значение поля содержит значение условия;
- `not_contains`: значение поля не содержит значение условия;
- `is_filled`: поле заполнено;
- `is_empty`: поле не заполнено.

Ошибки в одном условии не должны падать наружу на пациента. Resolver возвращает fallback и логирует ошибку.

## 11. Backend API для админ-раздела

Создать отдельный router, например:

- `backend/app/api/v1/endpoints/survey_routing.py`;
- prefix: `/api/v1/routing`;
- auth: существующая admin-сессия через `verify_admin_session` из `survey_editor.py` или вынесенный общий helper.

### 11.1. Получить клиники

`GET /api/v1/routing/clinics`

Ответ:

```json
{
  "items": [
    {
      "key": "novosibirsk",
      "title": "Новосибирск",
      "default_survey_config_id": 1,
      "is_enabled": true
    }
  ]
}
```

### 11.2. Получить настройки клиники

`GET /api/v1/routing/clinics/{clinic_key}`

Возвращает:

- настройки клиники;
- список правил;
- условия правил.

### 11.3. Сохранить опросник по умолчанию

`PUT /api/v1/routing/clinics/{clinic_key}/settings`

Payload:

```json
{
  "default_survey_config_id": 1,
  "is_enabled": true
}
```

### 11.4. CRUD правил

- `POST /api/v1/routing/clinics/{clinic_key}/rules`;
- `PUT /api/v1/routing/rules/{rule_id}`;
- `DELETE /api/v1/routing/rules/{rule_id}`;
- `POST /api/v1/routing/clinics/{clinic_key}/rules/reorder`.

Правило сохраняется вместе с условиями.

### 11.5. CRM-поля

`GET /api/v1/routing/crm-fields?search=&field_type=&active_only=true`

Ответ содержит поля из локального кэша.

`GET /api/v1/routing/crm-fields/{field_id}/options?search=`

Ответ содержит варианты списочного поля из локального кэша.

### 11.6. Ручная синхронизация

`POST /api/v1/routing/crm-fields/sync`

Запускает синхронизацию CRM-полей вручную для администратора.

Ответ:

```json
{
  "success": true,
  "fields_updated": 120,
  "options_updated": 350,
  "synced_at": "2026-05-04T00:00:00+03:00"
}
```

### 11.7. Проверить на сделке

`POST /api/v1/routing/clinics/{clinic_key}/test-deal`

Payload:

```json
{
  "deal_id": 12345
}
```

Поведение:

- backend загружает сделку из Bitrix24;
- применяет правила выбранной клиники;
- не создает ссылку;
- не записывает ничего в Bitrix24;
- возвращает результат и короткую причину.

Ответ:

```json
{
  "success": true,
  "clinic_key": "novosibirsk",
  "deal_id": 12345,
  "selected_survey_config_id": 2,
  "selected_survey_name": "Первичный прием",
  "selected_rule_id": 10,
  "selected_rule_name": "Невролог",
  "fallback_used": false,
  "reason": "Подошло правило \"Невролог\": поле \"Направление\" равно \"Неврология\"."
}
```

Если используется fallback:

```json
{
  "success": true,
  "clinic_key": "novosibirsk",
  "deal_id": 12345,
  "selected_survey_config_id": 1,
  "selected_survey_name": "Опросник по умолчанию",
  "selected_rule_id": null,
  "selected_rule_name": null,
  "fallback_used": true,
  "reason": "Ни одно активное правило не подошло. Использован опросник по умолчанию."
}
```

## 12. Frontend UI

Создать новый frontend route:

- `/routing` или `/survey-routing`.

Доступ:

- использовать существующую проверку admin-сессии через `useAdminAuth`;
- при отсутствии сессии редиректить на `/admin/login`, как редактор опросников.

Добавить ссылку на раздел из SQLAdmin, например кастомную кнопку/пункт рядом с "Визуальный редактор" и "Системный анализ".

### 12.1. Общий вид раздела

Первый экран - рабочий интерфейс, не landing page.

Основные зоны:

- выбор клиники;
- опросник по умолчанию;
- список правил выбранной клиники;
- кнопка "Проверить на сделке".

### 12.2. Выбор клиники

Клиники отображаются как вкладки или список.

В интерфейсе показывается только название клиники.

ID воронок Bitrix24 не показываются и не редактируются.

### 12.3. Опросник по умолчанию

Поле выбора опросника:

- список активных `SurveyConfig`;
- поиск по названию;
- отображать название и версию.

### 12.4. Список правил

Для каждой клиники отображается независимый список правил.

Колонки/поля:

- приоритет;
- активность;
- название;
- выбранный опросник;
- логика условий `AND`/`OR`;
- краткое описание условий;
- действия: редактировать, дублировать, удалить.

Нужно поддержать изменение приоритета:

- кнопки вверх/вниз или drag-and-drop;
- после изменения порядок сохраняется на backend.

### 12.5. Редактор правила

Форма правила:

- название;
- активность;
- опросник;
- логика условий `AND`/`OR`;
- условия;
- приоритет.

Условие:

- CRM-поле выбирается из списка с поиском;
- оператор выбирается из списка;
- значение зависит от типа поля.

Для списочных полей:

- значение выбирается из вариантов Bitrix24;
- в UI показывается текстовый label;
- сохраняется стабильный option ID.

Для текстовых/прочих полей:

- значение вводится вручную.

Расширенный режим:

- отдельная кнопка "Расширенный режим";
- после включения администратор может вручную ввести ID поля;
- UI должен явно помечать такие условия как ручные;
- ручной field ID сохраняется без требования наличия в локальном кэше.

### 12.6. Проверить на сделке

В общем разделе маршрутизации должна быть кнопка "Проверить на сделке".

Форма:

- выбранная клиника берется из текущей вкладки;
- администратор вводит ID сделки Bitrix24.

Результат:

- какой опросник был бы выбран;
- какое правило выбрано или что сработал fallback;
- короткая причина;
- без записи ссылки в Bitrix24.

## 13. Интеграция с Bitrix webhook

Изменить `backend/app/api/v1/endpoints/bitrix_webhook.py`.

Рекомендуемый порядок:

1. распарсить входной webhook;
2. проверить `auth_token`;
3. нормализовать `entity_type`;
4. для `DEAL` получить сделку через `Bitrix24Client.get_deal`;
5. определить клинику по `CATEGORY_ID`;
6. вызвать `SurveyRoutingService.resolve_for_deal(clinic_key, deal_data)`;
7. получить `survey_config_id`;
8. создать JWT с `lead_id`, `entity_type`, `survey_config_id`;
9. сохранить short code;
10. сформировать `/s/{short_code}`;
11. записать ссылку в поле сделки Bitrix24.

Если `BITRIX24_ALLOWED_CATEGORIES` включен, текущую фильтрацию воронок сохранить. Она должна выполняться до маршрутизации опросника.

Поле сделки для записи ссылки в первой версии остается текущим:

- `UF_CRM_1771160085`.

Желательно вынести его в settings:

- `BITRIX24_SURVEY_LINK_FIELD`.

## 14. Интеграция с `/survey/start`

Изменить `backend/app/api/v1/endpoints/survey.py`.

Требования:

- если token содержит `survey_config_id`, загружать этот `SurveyConfig`;
- если token не содержит `survey_config_id`, сохранить обратную совместимость;
- восстановление существующей сессии должно возвращать конфиг, привязанный к `existing_session.survey_config_id`, а не новый глобально активный конфиг;
- новая сессия сохраняет выбранный `survey_config_id`.

Отдельно исправить текущий потенциальный риск:

- сейчас при восстановлении сессии `survey_config` берется из заранее загруженного глобально активного конфига;
- после добавления маршрутизации это станет ошибкой, потому что разные сессии могут иметь разные опросники.

## 15. Безопасность и приватность

Нельзя логировать:

- полную сделку Bitrix24;
- персональные данные пациента;
- значения чувствительных CRM-полей.

Можно логировать:

- `deal_id`;
- `clinic_key`;
- `survey_config_id`;
- `rule_id`;
- технический reason code.

Admin API должен использовать существующую admin-сессию.

Нельзя хранить Bitrix webhook URL, токены или секреты в репозитории.

## 18. Не входит в первую версию

В первую версию не включать:

- визуальную настройку связи клиника-воронки;
- сложные вложенные группы условий;
- числовые сравнения больше/меньше;
- regex;
- маршрутизацию по лидам, если основной сценарий работает со сделками;
- историю всех проверенных правил;
- массовый пересчет уже созданных ссылок;
- изменение медицинской JSON-логики опросников.

## 19. Критерии готовности

Функция считается готовой, если:

- администратор может выбрать клинику;
- администратор может задать default-опросник клиники;
- администратор может создавать, редактировать, удалять и переупорядочивать правила;
- CRM-поля и варианты списков подтягиваются из Bitrix24 и кэшируются в БД;
- ручной ввод CRM field ID доступен только через расширенный режим;
- "Проверить на сделке" показывает выбранный опросник и короткую причину без записи в Bitrix24;
- webhook выбирает опросник до генерации ссылки;
- `/survey/start` использует выбранный `survey_config_id`;
- при ошибках используется fallback-опросник;
- логи не содержат персональные данные и полные payload сделки;
- покрыты ключевые unit/API тесты;
- production проверен по чек-листу после деплоя.
